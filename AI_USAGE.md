# AI Usage & Development Transparency

C.O.D.A. (Coda) is an open-source project developed with significant assistance from artificial intelligence.

This document explains how AI is used during development, which responsibilities remain with the maintainer, and how I balance AI-assisted development with improving my own software engineering skills.

The intention is transparency, not to suggest that AI-assisted development is inherently better or worse than traditional development.

## 1. Development Philosophy

Coda is both a long-term software project and a personal learning experience.

I want to build a capable, extensible assistant while continuing to develop my own understanding of Python, software architecture, debugging, and engineering practices.

AI development tools allow me to explore ideas, prototype functionality, and make progress on larger features that would otherwise take considerably longer to implement independently.

However, I also recognise that having an AI generate working code is not the same as understanding how that code works.

My approach is therefore to balance two priorities:

- **Project development:** Using AI assistance where it helps deliver functionality, improve quality, and maintain momentum.
- **Personal development:** Deliberately reserving selected tasks for hands-on implementation, independent research, experimentation, and debugging.

I do not intend to eliminate AI from my development workflow, nor do I intend to delegate every programming challenge to it.

## 2. History of AI-Assisted Development

Coda was not originally developed with the same level of AI assistance used today.

**Substantial AI-assisted development began around v1.2.0**, as AI coding tools became a more significant part of my workflow.

Before this point, development was predominantly undertaken manually, although this should not be interpreted as a guarantee that no AI assistance was used.

Since approximately v1.2.0, Codex has taken an increasingly active role in implementation, refactoring, testing, documentation, and repository maintenance.

This represents a change in development methodology rather than a change in project ownership or direction.

The version boundary is approximate, not a formally audited provenance cutoff. Individual contributions may have involved different levels of assistance on either side of it.

## 3. AI Tools Used

The primary AI tools used in Coda's development include:

| Tool         | Typical usage                                                                                                                |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| OpenAI Codex | Code generation, implementation, refactoring, testing, documentation, repository maintenance, and development automation.    |
| ChatGPT      | Architectural discussions, design exploration, planning, debugging assistance, technical explanations, and learning support. |

Other tools or models may be used as development workflows evolve.

The use of an AI tool does not imply that every suggestion or generated change has been accepted without modification.

## 4. Where AI Has Been Used

AI has contributed substantially to Coda's development, including:

### Implementation

Codex has been used to implement significant portions of the codebase, including features, supporting infrastructure, tests, refactoring, and integration work.

Some changes are generated largely autonomously, while others follow requirements, implementation decisions, or architectural designs that I have established.

I do not claim that all source code has been written manually.

### Architecture and Planning

AI has assisted with:

- Exploring architectural alternatives and their trade-offs.
- Designing component interfaces and integration approaches.
- Planning features, milestones, and development priorities.
- Identifying potential failure cases and security considerations.
- Reviewing existing implementations and suggesting improvements.

These discussions inform development decisions but do not automatically determine them.

### Documentation

**The overwhelming majority of Coda's documentation has been authored or substantially generated by Codex.**

An exception is the project's early release notes, which were written before the current AI-assisted documentation workflow.

Documentation may be generated from repository contents, existing implementation details, development discussions, or instructions I provide.

AI authorship of documentation should not be interpreted as independent verification of its technical accuracy.

### Testing and Debugging

AI tools have assisted with generating tests, investigating failures, interpreting errors, and proposing fixes.

Where appropriate, I also run software, inspect its behaviour, and perform manual testing.

A generated test passing is not, by itself, evidence that a feature is correct, secure, or production-ready.

## 5. Where I Prioritise Independent Development

Some work is deliberately reserved for personal learning.

For these tasks, I aim to:

1. Understand the problem and describe the intended behaviour.
2. Break the problem into smaller steps.
3. Translate those steps into code independently.
4. Use documentation, examples, debugging tools, and experimentation to resolve problems.
5. Seek AI assistance when necessary.
6. Review the completed implementation and identify what I still need to learn.

One example is the first-party filesystem MCP integration, where I have deliberately taken a more hands-on approach to implementing filesystem operations and permission handling.

This does not mean these features are entirely human-written. AI may still contribute explanations, implementation suggestions, reviews, or code when needed.

**The purpose of these exercises is to develop independence, not to enforce an artificial prohibition on assistance.**

Learning-focused tasks should also remain reasonably scoped so they do not indefinitely block broader project development.

## 6. Where AI Is Restricted

The following principles govern the use of AI in the development workflow.

### Security-Sensitive Changes

AI may assist with security-related implementation, auditing, and testing.

However, security-sensitive changes should receive deliberate review and appropriate validation before acceptance.

Generated code must not be assumed secure merely because it is functional or accompanied by passing tests.

### Credentials and Sensitive Information

Secrets, credentials, private keys, and other sensitive information should not be deliberately included in prompts, development logs, or public documentation.

AI tools should receive only the information necessary to perform their tasks, subject to the capabilities and access permissions of the tools being used.

### Destructive or High-Impact Operations

Destructive changes, irreversible operations, and actions affecting important infrastructure or data should require appropriate human authorisation.

Autonomous tooling should operate within explicitly defined permissions and should not be granted unrestricted authority by default.

### Project Direction

AI may recommend features, priorities, designs, or changes, but the final decisions about Coda's direction remain mine.

This includes decisions about the roadmap, accepted contributions, releases, and architectural trade-offs.

## 7. Review, Responsibility, and Ownership

I remain responsible for maintaining Coda and deciding which changes are accepted into the project.

However, the level of manual review and independent understanding may vary between contributions.

I do not claim to have personally written, reviewed line by line, or fully understood every part of the codebase.

**Improving my understanding of Coda's existing implementation is an ongoing development objective.**

To support this, I have established a dedicated [CODA Classroom Mode discovery milestone](https://github.com/mattordev/coda/milestone/6).

Classroom Mode is an exploratory initiative intended to investigate how Coda could support structured, repository-aware learning and help me develop a deeper understanding of the software I maintain.

The discovery work includes exploring competency tracking, evidence-based assessments, persistent learning records, Git-aware lesson context, and ways to adapt AI development assistance based on demonstrated understanding.

The longer-term ambition is to make AI assistance more effective not just at producing working software, but at helping me understand, modify, and eventually implement more of that software independently.

**Classroom Mode has not yet been committed to a release version or implementation architecture.** Its milestone is intentionally undated, with further development dependent on the findings of the discovery phase.

Where AI-generated changes introduce defects, those defects are treated as project issues requiring investigation and correction, rather than being dismissed because of how the code was produced.

## 8. Contribution Transparency

Contributors are welcome to use AI-assisted development tools.

Where practical, pull requests should disclose meaningful AI involvement, particularly when substantial code or documentation has been generated.

A useful disclosure may include:

- Which AI tools were used.
- Whether AI generated code, tests, documentation, or design suggestions.
- What the contributor personally implemented or reviewed.
- What testing or validation was performed.

The purpose is to provide useful context for reviewers, not to penalise contributors for using AI.

AI-assisted contributions should be evaluated against the same expectations for correctness, maintainability, security, and compatibility as other contributions.

## 9. Historical Limitations

Coda has evolved through multiple development approaches, and complete AI provenance records do not exist for every historical change.

Consequently, this document describes known development practices rather than providing an exhaustive, line-by-line attribution of the repository.

A commit authored under my Git identity does not necessarily mean every line was manually written by me.

Likewise, an AI-assisted commit may contain substantial human-written implementation or design work.

Future pull requests and development records may provide more detailed disclosures where useful.

## 10. AI Used by Coda vs. AI Used to Develop Coda

This document concerns AI assistance used during the **development of Coda**.

Coda itself is an AI-powered assistant that can use language models and supporting services at runtime.

These are separate concerns:

- **Development-time AI:** Tools used to write, review, plan, test, and document the project.
- **Runtime AI:** Models and services used by Coda to interpret requests, generate responses, and support assistant functionality.

The presence of AI-generated source code does not necessarily mean that code makes AI model calls during execution.

Likewise, manually written code may implement features that depend heavily on runtime AI.

## 11. Ongoing Commitment

My long-term goal is to become increasingly capable of independently designing, implementing, debugging, and maintaining Coda.

I expect the way I use AI to change as my skills and the project mature.

I do not view independent development and AI-assisted development as mutually exclusive.

**Coda is a project I direct, maintain, and take responsibility for, built with substantial AI assistance and an ongoing commitment to learning.**
